Scheduled `update` events aggregate by default into a fixed 60-second window.
Version **4.1.0** keeps the latest event fields at the root, adds `timestamp` and
`aggregated_events`, and sends delivery metadata in HTTP headers. The fixed
60-second window remains unchanged. Immediate delivery, its retries, non-update
actions and legacy opt-out retain their existing format; the framework does not
add stacking fields or delivery headers on those paths.

## Upgrade from 3.0.0 or 4.0.0

**4.1.0 changes the wire format within the 4.x series.** Update consumers before
upgrading: `_wpwf` is no longer generated, and `aggregated_events[n].payload.id`
becomes `aggregated_events[n].id`. Read the delivery ID and window from the headers
shown below. Root `id`, `entity`, `action` and `rest_url` stay in place for n8n.

`timestamp` is now reserved. Rename custom fields using this name or opt out of
stacking. Previously accepted events with conflicting custom fields retain their
old format, including when only an earlier history entry conflicts. Already sealed
3.0.0/4.0.0 JSON bodies are never rewritten. New delivery headers are also added to
those requests. Drain old stacks first, or temporarily accept both formats.
A delivery header alone therefore does not identify the body's schema.

Unsealed stacks without collisions adopt the new format. No database migration is
needed. After the body filter runs for the first attempt, the exact JSON is frozen
across retries; the latest event and history can change only before sealing.

## Keep the existing behavior

Call `$webhook->stack_updates( false )` when configuring a webhook to retain the
flat body, five-second initial delay, and first-pending-payload deduplication.
Opting out does not turn legacy scheduling into a complete per-event stream.
Already accepted stacks finish even after opting out.
Configure this consistently on every request and worker that loads the webhook.

## Window and identity

The first accepted update fixes the opening time and exclusive cutoff (60 seconds later).
Updates at seconds 0, 20 and 59 share a stack; one at second 60 opens another.
A delayed worker does not extend the old window. Execution depends on the site's
Action Scheduler runner, so `wpwf-window-closed-at` is the fixed temporal cutoff,
not the actual send time. Capacity overflow may stop acceptance earlier and open
an overlapping window without moving that cutoff.

Stack identity includes destination URL, registered webhook name and configured
headers, entity type and ID. Numeric ID `42` and string `"42"` match. Different
header sets stay separate. Meta events also include `meta_type`, separating post
and user meta with the same object ID. Different meta keys join the same window
and are all retained as separate entries. Header filters run later, per attempt;
their results cannot change already accepted window membership.

Events are ordered by acceptance under the database lock. Their timestamps have
UTC second precision; array order resolves equal timestamps. Capacity overflow opens an additional
window starting with the overflowing event; existing deadlines never move. No field merging or
event deduplication occurs inside a stack. Events arriving during delivery belong
to a later window and cannot be removed when the older delivery is acknowledged.
Separate windows may be delivered out of order when an older one retries.

## Wire format

The latest complete notification remains at the root: `action`, `entity`, `id`,
`rest_url` and custom fields keep their original paths. Each event has its own
`timestamp`, meaning acceptance by this library, not the source's modification time.
`aggregated_events` contains all accepted event objects, including the latest,
without `payload` wrappers. A single-event window uses the same format with one entry.
No fields from earlier events are merged into the latest notification.

`timestamp` and `aggregated_events` are reserved. New events using either field,
even with null values, are rejected visibly before acceptance rather than overwritten.
Other custom fields, including `_wpwf`, `payload` and `delivery_id`, remain untouched.

```json
{
  "action": "update",
  "entity": "meta",
  "id": 42,
  "meta_type": "post",
  "meta_key": "price",
  "timestamp": "2026-11-15T15:00:20Z",
  "aggregated_events": [
    {
      "action": "update",
      "entity": "meta",
      "id": 42,
      "meta_type": "post",
      "meta_key": "title",
      "timestamp": "2026-11-15T15:00:00Z"
    },
    {
      "action": "update",
      "entity": "meta",
      "id": 42,
      "meta_type": "post",
      "meta_key": "price",
      "timestamp": "2026-11-15T15:00:20Z"
    }
  ]
}
```

Delivery headers for this example:

```http
wpwf-delivery-id: 12345
wpwf-window-opened-at: 2026-11-15T15:00:00Z
wpwf-window-closed-at: 2026-11-15T15:01:00Z
```

- `wpwf-delivery-id`: the original Action Scheduler ID as a header string. It stays
  unchanged across retries. Deduplicate by source site plus ID; IDs are not globally unique.
- `wpwf-window-opened-at`: first acceptance time in UTC.
- `wpwf-window-closed-at`: exclusive temporal cutoff in UTC, fixed at opening plus 60 seconds.

These three headers are derived from durable state on every attempt and applied
**after** `wpwf_headers`. Case-insensitive duplicates from configured headers or
filters are replaced. Authentication headers may still refresh per attempt. The
protected delivery headers are not stored in the aggregation identity.

In n8n, use `$json.body.id` and `$json.headers['wpwf-delivery-id']`. If forwarding or
archiving only the body, explicitly keep any delivery headers needed for deduplication
or diagnostics. A body-only signature does not authenticate these headers.

The private storage token is never exposed. The body has no generated `_wpwf`,
`schema_version`, or delivery ID. The history array length supplies the event count.

## Payloads and filters

Built-in post/term/user notifications do not capture full entity snapshots.
Enrichment adds `post_type`, `taxonomy`, `roles` and `rest_url` when available.
Meta notifications include `meta_type`, `meta_key` and optional ACF identifiers;
they do not automatically include old/new values. Custom emitters and filters
can add such values, nulls, lists and nested objects. Fetch the current resource
when the receiver needs authoritative entity state.

`wpwf_payload` runs for every incoming event before aggregation. Returning false
or null suppresses that event. Stacked mode captures enrichment at acceptance;
legacy and immediate modes keep their delivery-time enrichment. Historical
entries are notification contents, not an audit log or reconstructed entity states.
Upstream WordPress hooks may already suppress events before they reach this queue.

`wpwf_request_body` receives the root event with timestamp and flat history once, immediately before the
first attempt. Its identity arguments describe the stack; its payload argument
is the latest complete event body. Filters must handle this schema or opt out of
stacking. Ordinary nested JSON objects are exposed as associative PHP arrays for
filter access such as `$body['billing']['email']`. Empty objects and
objects with list-shaped numeric keys remain `stdClass` to preserve their JSON
object shape. The resulting JSON is persisted unchanged for retries. `wpwf_headers`
runs on every attempt, allowing authentication headers to refresh.

## Persistence, recovery and limits

Payloads live in non-autoloaded internal WordPress options, outside Action Scheduler
arguments and the option cache. Per-identity database locks serialize acceptance;
a separate send lock prevents overlapping HTTP attempts for one stack. Enqueue
looks up only that stack's action, avoiding hydration of unrelated pending jobs.

Stacking requires the standard WordPress `wpdb` class, MySQL 5.7.5+ or MariaDB
10.1+, and named-lock support on the primary connection. Database subclasses such
as Query Monitor (`db.php`), HyperDB and LudicrousDB conservatively fall back to legacy dispatch, even when
`stack_updates(true)` is configured: unknown routing must not overwrite events
through stale reads. Older database servers also use legacy dispatch. This means
receivers must support flat bodies on those installations. Existing stacks are
retained and fail visibly if the database becomes unsupported; drain them before
changing database infrastructure. Recovery wake-ups complete without processing stacks while the connection is unsupported,
then schedule a unique successor after completion. This keeps recovery alive without reading or modifying stack payloads through an
unsupported connection. After restoring the standard database class, that wake-up
resumes recovery even if no new update is emitted. Query Monitor is not allowlisted:
the class guard is deliberately conservative, including non-routing subclasses.
MariaDB's legacy `5.5.5-` compatibility prefix is stripped before checking its
actual server version. If the server disables `GET_LOCK`, acceptance fails visibly;
configure `stack_updates( false )` on that installation. No schema migration or
custom table is needed.

Limits are 100 accepted events and 256 KiB of JSON per unsealed record, including
routing metadata. If an otherwise valid event would overflow a window, it opens
an additional window with a new action/delivery ID and its own 60-second deadline.
For example, 105 small updates can become batches of 100 and 5. The full window
stays unchanged; all events are retained. A single event too large to fit on its
own is rejected visibly with `webhook_stack_capacity_exceeded`. Nothing is
truncated or silently evicted. The final filtered JSON body is limited to
1 MiB; invalid or oversized filter output fails the action before HTTP. Direct
dispatcher calls throw `WP_Exception`; `Webhook::emit()` uses its existing warning
path. Monitor warnings and failed scheduler actions, especially for high-volume entities.

Recovery is armed when attempting to accept a stack, with one pending single action
300 seconds ahead. Each pass visits up to 100 records, advances a cursor, and
arms the next pass before processing. Scheduler failure/timeout hooks restart a
recovery worker that died before arming its successor. It cancels pending recovery work once the
store is empty. Thus sites that never attempt stacking have no recovery jobs or per-request
recovery query, and idle sites do not accumulate perpetual recovery logs. Registration
and acceptance share a short database mutex so idle retirement cannot strand work.
It repairs missing scheduling and retries abandoned
attempts after Action Scheduler marks them failed. A canceled action with a live
record is also recovered; canceling only the scheduler action does not discard
accepted work. Recovery needs a functioning scheduler and database.

Configured retry limits, backoff and URL blocking apply. Stacking computes the
retry delay before each attempt to persist recovery timing, even if that attempt
eventually succeeds. Each preparation/delivery attempt is counted and persisted before consumer body
and retry-delay filters run, so a fatal body filter also consumes the retry budget.
An interruption before preparation finishes uses a 300-second recovery delay;
successful preparation replaces this with the configured backoff. The
`wpwf-retry-count` header counts preparation attempts too, so it may be non-zero
on the first HTTP request after an interrupted preparation.
With `max_retries( 0 )`, an interrupted attempt is not sent again. Normal success
and terminal failure remove the stored payload; corrupt or temporarily inaccessible
records remain for diagnosis/recovery and produce error logs. Completion-callback
failures are logged and deferred to recovery so they cannot abort unrelated jobs.
Throwing HTTP failure listeners do not cancel remaining retry attempts.
A stopped queue retains
accepted records and can grow; keep it running and monitor backlog/storage.

Each stack uses the same `wpwf-stacks` scheduler group. Identity locks plus exact
argument lookup prevent duplicate scheduling without permanent per-window group
rows or dependence on version-specific native uniqueness rules.

Before removing the library or downgrading to 2.x, drain accepted stacks or deliberately remove their
internal records and queued actions as part of the consuming plugin's cleanup.
Version 2.x cannot process stack records, so downgrading with live stacks strands them.
The recovery action is not recurring, so removal cannot leave an endless recurring
job; stored payloads are deliberately not silently deleted on deactivation.

An HTTP request may succeed before its sender crashes or loses the response.
Redelivery is therefore possible: receivers must be idempotent. Stable IDs and
frozen retry bodies support deduplication; they do not provide exactly-once HTTP.
See [failure handling](./failure-handling.mdx) and [testing](./testing.mdx).
