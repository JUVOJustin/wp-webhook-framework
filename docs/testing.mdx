Use the bundled `wp-env` application test setup to validate how the framework behaves inside WordPress.

PHPUnit uses the WordPress core test bootstrap in the development container.
Real HTTP deliveries go to `http://tests-wordpress`, the second wp-env site with
its own database. This prevents sender test transactions from locking receiver
log writes. Background runners are disabled in these fixtures; tests explicitly
advance the queue.

## What the suite covers

- `wp-env` mounts the primary and secondary fixture plugins plus a receiver MU plugin used to capture real HTTP webhook deliveries.
- Each fixture plugin loads the shared library from the repository checkout and calls `Service_Provider::register()` on its own, which also loads the bundled Action Scheduler.
- `tests/phpunit/bootstrap.php` loads the same fixture plugin entrypoints for the WordPress core test bootstrap, because that bootstrap uses its own isolated install state.
- The primary fixture consumer registers built-in post, term, user, and custom webhooks.
- The secondary fixture consumer registers its own post webhook to validate multi-plugin usage.
- PHPUnit tests execute scheduled Action Scheduler jobs, call real HTTP receiver endpoints, and assert persisted delivery logs.
- The GitHub Actions workflow runs the same suite on every push and pull request.

## Action Scheduler resolution

`Service_Provider::bootstrap_action_scheduler()` checks two paths. The first is the production layout, where the framework sits in a consumer's vendor tree and Action Scheduler resolves at `../../../woocommerce/action-scheduler`. The second covers this repository checked out on its own, where `vendor/` lives inside the checkout — which is how the suite runs it, so the suite exercises the second path.

:::caution
Do not try to recreate the production layout with a `.wp-env.json` mapping pointing into `vendor/`. On a fresh checkout that path does not exist when `wp-env start` runs, because `composer:install` runs afterwards inside the container. On Linux, Docker then creates the missing source as a **root-owned** directory, and the subsequent `composer install` fails with `vendor/composer does not exist and could not be created`. Docker Desktop on macOS behaves differently, so this passes locally and breaks CI.
:::

## Commands

```bash
pnpm install
pnpm run wp-env:start
pnpm run composer:install
pnpm run test:phpunit
pnpm run test:concurrency
pnpm run wp-env:stop
```

## Key files

- `.wp-env.json` mounts the repository checkout and maps the receiver MU plugin.
- `tests/phpunit/bootstrap.php` loads fixture plugin entrypoints into the WordPress core PHPUnit bootstrap.
- `tests/wp-env/mu-plugins/wpwf-test-receiver.php` handles incoming webhook HTTP requests and exposes log/reset endpoints for assertions.
- `tests/wp-env/plugins/wpwf-test-app/wpwf-test-app.php` boots the shared framework from the primary plugin and defines its fixture hooks.
- `tests/wp-env/plugins/wpwf-test-secondary/wpwf-test-secondary.php` boots the shared framework from the secondary plugin and defines its fixture hooks.
- `tests/phpunit/includes/class-wpwf-webhook-test-case.php` provides helpers for receiver log management and queued action execution.
- `tests/phpunit/PostWebhookCrudTest.php`, `tests/phpunit/TermWebhookCrudTest.php`, and `tests/phpunit/UserWebhookCrudTest.php` provide separate CRUD examples per entity.
- `tests/phpunit/MetaWebhookTest.php` covers meta emission modes, parent entity updates, and delivery payload enrichment.
- `tests/phpunit/DeliveryModeTest.php` covers scheduled vs immediate dispatch behavior.
- `tests/phpunit/WebhookFilterTest.php` covers runtime filters for delivery mode, URL routing, payload suppression, headers, and request body changes.
- `tests/phpunit/WebhookFailureHandlingTest.php` covers retries, backoff scheduling metadata, and URL blocking behavior.
- `tests/phpunit/NotificationAndFailureStateTest.php` covers blocked email notifications and expired-block recovery.
- `.github/workflows/integration-tests.yml` runs the suite in CI.

## Extending the suite

Add new application tests under `tests/phpunit`. Reuse `WPWF_Webhook_Test_Case` when you need to:

- inspect pending `wpwf_send_webhook` and `wpwf_send_update` actions with their durable snapshots
- execute scheduled actions immediately
- assert receiver log entries (URL, headers, payload, webhook name)

This keeps future validation tests focused on webhook behaviour instead of environment setup.

## Action Scheduler compatibility

CI covers WordPress 6.7 with Action Scheduler 3.9.3, WordPress 6.9 with
Action Scheduler 4.2.0, and current WordPress with the locked scheduler version.
The Composer constraint permits later 4.x releases; those releases still need
the application suite before being considered verified.

`ActionSchedulerCompatibilityTest.php` covers large payloads, independent identities,
queue-runner completion and rejected scheduling requests.
`ActionSchedulerNativeUniquenessTest.php` pins the 4.2 native-store contract for
complete arguments, argument ordering, running actions and uniqueness release.
These native 4.2 assertions skip on 3.x.

`UpdateCoalescingTest.php` covers latest hints and headers, in-flight changes,
retries, recovery, opt-out, legacy jobs and authoritative resource retrieval.
These scenarios exercise the native store, with an additional in-flight
regression for the migration HybridStore.
`tests/concurrent-updates.php` launches eight separate PHP processes against the
native database store, checks that every enqueue succeeds and only one action
exists, then verifies real HTTP delivery of the last update and state cleanup.
Run it with `pnpm run test:concurrency` after the PHPUnit suite. CI runs both.

To exercise a different supported scheduler version in the running wp-env:

```sh
pnpm exec wp-env run cli --env-cwd=wp-content/wpwf-framework composer update woocommerce/action-scheduler:4.2.0 --with-dependencies
pnpm run test:phpunit
```

This changes the local Composer lockfile; restore the intended locked version
after testing. Local Docker runs take about 8–10 seconds for PHPUnit, 6 seconds for the
concurrency test, and 20–70 seconds for environment setup with available images. Integration jobs
have a 20-minute maximum including setup. Container commands cap PHPUnit at
120 seconds and the concurrency probe at 90 seconds, with a five-second kill
grace. The probe bounds each worker wait at 30 seconds and terminates its
remaining workers on failure.

## Local hooks and dependency updates

`pnpm install --frozen-lockfile` installs the pinned tools and Lefthook hooks.
Keep wp-env running before committing or pushing: staged PHP is formatted on
commit; a push runs PHPCS, PHPStan and both application test commands. The full
WordPress/Action Scheduler compatibility matrix runs in CI.

Dependabot checks npm, Composer and Actions weekly, with separate patch, review
and security groups. Verified patch updates can merge only after both CI workflows
and every other reported check/status succeed for that exact commit. Minor and
major updates remain manual. The merge workflow never checks out PR code. It re-evaluates open Dependabot PRs
when classification, CI or external checks/statuses finish, including reruns.
Classification and merging have three- and five-minute job limits and perform
no polling waits. Failed or stale heads remain open.

The WordPress 6.7 job installs the separate committed scheduler fixture under
`tests/fixtures/action-scheduler-3.9` and overlays only that package in the main
vendor tree. Both dependency sets use frozen Composer installs; CI never resolves
new versions. Update and commit the fixture lockfile explicitly when changing
the legacy compatibility target.
