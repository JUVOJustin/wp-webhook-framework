Automatic failure monitoring, retry mechanism, and blocking system for webhook reliability.

For email notifications and custom handlers, see [Notifications](./notifications.mdx).

## Critical Distinction: Retries vs. Blocking

| Concept | Scope | Configuration |
|---------|-------|---------------|
| **Retry** | Single webhook event | `max_retries()` |
| **Blocking** | All webhooks to a URL | `max_consecutive_failures()` |

**Retry**: Framework automatically retries a single failed webhook event (e.g., "Post #123 update") with exponential backoff.

In `Delivery_Mode::IMMEDIATE`, the first attempt runs in the current request and failed retries are still queued in Action Scheduler.

**Blocking**: Stops all webhooks to a URL after multiple delivery attempts have failed (including retries), preventing resource waste on dead endpoints.

## Retry Mechanism

### Configuration

```php
$webhook->max_retries( 3 )  // Retry 3 times before giving up (default: 0)
        ->timeout( 30 );     // 30 second timeout per attempt
```

### Exponential Backoff

Failed webhooks are retried with increasing delays:

| Retry | Delay |
|-------|-------|
| 1 | 1 minute |
| 2 | 2 minutes |
| 3 | 4 minutes |
| 4 | 8 minutes |

The framework schedules retries explicitly; an Action Scheduler failure does not
automatically retry a one-off action. A blocked URL also prevents queued retries
from making HTTP requests.

Retry count is tracked in `wpwf-retry-count` header.

### Customizing Retry Delays

```php
// Static 5-minute delay for all retries
add_filter( 'wpwf_retry_delay', fn() => 300 );

// Faster retries for critical webhooks
add_filter( 'wpwf_retry_base_time', function ( int $base, string $name, int $count ): int {
    return 'critical_webhook' === $name ? 10 : $base;
}, 10, 3 );
```

## Failure Tracking & Blocking

### Flow

1. **Webhook fails** → A retry is queued when allowed by `max_retries()`
2. **Each failed attempt** → Failure count incremented for URL, including retries
3. **Threshold reached** → URL blocked, `wpwf_webhook_blocked` action fired
4. **Success or expired block window** → Counter reset, URL unblocked

### Configuration

```php
$webhook->max_consecutive_failures( 10 ); // Block after 10 failed attempts (default)
$webhook->max_consecutive_failures( 0 );  // Disable blocking entirely
```

**Disabling blocking:** When set to 0:
- `wpwf_webhook_failed` action still fires
- Failure counts are not tracked
- `wpwf_webhook_blocked` never fires
- Webhooks continue regardless of failures

## Failure Data Structure

Per-URL state stored in transient `wpwf_failures_{md5($url)}`:

```php
array(
    'count'               => 5,          // Failed attempts, including retries
    'first_failure_at'     => 1234567890, // Window start timestamp
    'blocked'              => true,       // Blocked status
    'blocked_time'         => 1234567890, // Block timestamp
)
```

**Expiration:** 1 hour. When a blocked URL is checked after that window, the framework starts a fresh failure window instead of carrying the old failure count forward.

## Webhook Status Actions

For detailed action documentation, see [Hooks and Filters](./hooks-and-filters.mdx#actions).

| Action | When Fired |
|--------|------------|
| `wpwf_webhook_success` | Successful delivery |
| `wpwf_webhook_failed` | Each failed delivery attempt |
| `wpwf_webhook_blocked` | URL blocked |

## Default Settings

| Setting | Value |
|---------|-------|
| Failure Threshold | 10 consecutive failed attempts |
| Block Duration | 1 hour (auto-unblock) |
| Retry Attempts | 0 (disabled) |
| Retry Base Time | 60 seconds |

## Implementation

**Files:** `src/Dispatcher.php`, `src/Failure.php`, `src/Webhook.php`

**Key methods:**
- `Dispatcher::dispatch_immediately()` - Sends immediate first attempt and queues retries on failure
- `Dispatcher::schedule_retry_if_applicable()` - Schedules retry with backoff
- `Webhook::calculate_retry_delay()` - Calculates exponential delay
- `Dispatcher::trigger_webhook_failure()` - Tracks failures, fires actions

## Stacked update retries

[Stacked updates](./update-stacking.mdx) retain the original action's integer
`_wpwf.delivery_id` and the exact sealed JSON across retries. A retry can have a different
Action Scheduler ID. New events create later windows and do not overwrite retry
content or reset its budget. A hard exit during body preparation or HTTP consumes that
attempt; recovery waits for the scheduler to mark abandoned work failed.
`max_retries( 0 )` also disables retries after such interruptions.

A full window starts an additional window for the next event without dropping
accepted events. Only a single event too large to fit is rejected through the
existing warning/exception path. Invalid final body filters, removed registrations,
blocked destinations and exhausted attempts fail without sending and remove the
stored stack. HTTP delivery failures continue to fire the existing failure hooks.

A throwing HTTP failure listener does not discard a stack's remaining retries.
Errors while scheduling from a completion/failure callback are logged and left
for recovery, allowing the runner to continue with unrelated actions.
